# 对话页行计划：从「藏哪些」改成「画哪一行」

状态：第 3 步已实施（前端只按行计划显示），第 4 步（删旧字段）待做。

## 问题

宿主的对话页把每条 append 来源的消息永久画出来，替换只对模型生效（`isAppendSurfaceEvent`）。Tavern 改写历史（重新生成、回退、撤销回退、编辑正文、修复模型上下文）后，只能事后把不该看到的行藏掉。现在藏行靠这些名单叠加：

| 名单 | 算在哪 | 管什么 |
| --- | --- | --- |
| `suppressedDshTurns` | 存档 + `foregroundSuppressedTurns` + `regenerationInputTurns` | 生成期回合、回退回合、中止的回合 |
| `replacingDshTurns` | 存档 | 重新生成进行中的旧正文 |
| `supersededDshTurns` | `supersededRegenerationTurns`（日志） | 正文已被替换、宿主仍会画的回合 |
| `regeneratedDshTurns` | 存档 + `projectedReplyTurns`（日志覆盖） | 剧情轮 → 画正文的原生轮；既用来显示，也用来藏 |
| 浏览器 localStorage 三份 | 前端 | 旧版本留下的隐藏轮、回退轮、生成期输入 |

前端 `turn-history.js` 按顺序执行 7 个 apply，后一个可以推翻前一个；`assistant-renderer.js` 里还有一处按 `replacingDshTurns`/`suppressedDshTurns` 提前返回。规则之间互相依赖，例如 `supersededRegenerationTurns` 要先拿到映射才能决定保留哪一轮，而映射又会被 `applyRegeneratedDshTurns` 拿去按剧情轮号去藏原生轮。

近一个月这一块有 81 条提交，最近 3 天修了 6 次「重新生成后空白或重复」（#283、#304、#307 及其前后）。每次都在某一张名单上加特例；消息顺序一变（工具提交的折叠副本、编辑轮、宿主插入的 developer 消息）就有新的组合漏掉。

## 决定

服务端从「存档 + 会话日志」一次算出**行计划**：每个剧情轮由哪个原生轮画输入、哪个原生轮画正文。前端只认这一份计划，**白名单**显示：属于计划的行显示，计划之外、已结束的原生轮一律藏。不再有多张名单互相覆盖。

写入侧（重新生成、回退、修复怎么写会话）不动；宿主不动。

## 行计划

```js
// domain/transcript-row-plan.js（纯函数）
planTranscriptRows({ chat, events, nodes }) → {
  version: 1,
  rounds: [{ story: 10, input: 10, reply: 13 }, ...], // 剧情轮 → 画输入/正文的原生轮
  // 例外表里另有 { input: 1, reply: 0, kept: 1 }：作废轮只画玩家那一行
  open: 14 | null,   // 进行中或尚未入档的原生轮：原样显示，不藏
  // 失败轮另有错误控件，沿用现有 hiddenDshErrorTurns 等字段，不并入
}
```

推导规则，按顺序，每条只做一件事：

1. **剧情轮来自存档。** 存档的每条非开场 assistant 行是一个剧情轮，`story = message.turn`；开场轮固定。
2. **输入行 = 这一轮自己的原生轮。** 玩家输入永远画在原来的位置；重新生成不换输入。
3. **正文行 = 日志里这一轮正文可画的那条 append 所在的原生轮。** 先看当前生效的、带 `tavernStoryTurn` 的替换：区间末端是 assistant append 就取它；否则取区间之后的投影副本；再否则取区间内最后一条有文字的 assistant append。都没有就是 `story` 自己。这正是 `projectedReplyTurns` 和投影补副本现在各自的判断，合成一处。
4. **计划之外、已结束的原生轮都不画**：生成期输入、旧正文、编辑轮、回退掉的轮、中止的尝试，不再逐类判断。
5. **`open`**：最后一个原生轮还在跑，或已结束但存档还没有对应行（结算中、#196 待补记），原样显示，免得生成中整楼消失。
6. **失败轮的输入被重试采用时，只画玩家那一行**（`kept: 1`）：重试把正文写在另一个原生轮，作废的那一轮不是任何剧情轮，整轮藏掉会把玩家自己发的话一起藏了。`kept` 轮只显示 `user`/`steering` 行，失败残留、触发卡和尾行都不画；名单来自视图的 `keptInputTurns`（`keptPlayerInputTurns` 从日志算）。

前端规则（替换 `turn-history.js` 的 7 个 apply 和 assistant-renderer 里的提前返回）：

- 原生轮 T 的输入类行（`user`、`turn-trigger`）：T 是某轮的 `input`，或 T 是 `open`，才显示。
- 原生轮 T 的正文类行（`assistant-step`、`turn-process`、`turn-tail`）：T 是某轮的 `reply`，或 T 是 `open`，才显示；剧情轮号由 `rounds` 反查（替换 `tavernStoryTurnForDshTurn`）。
- `context` 类行、错误行照旧由现有逻辑处理。
- localStorage 三份名单停用，只读一次做迁移后清掉。

非剧情会话（卡片工作台、后台会话）不下发计划，前端什么都不藏，和现在一样。

## 兼容

- 视图字段：新增 `transcriptRows`；`regeneratedDshTurns` 保留一个版本给插件和旧前端，值由计划生成；`suppressedDshTurns` 等不再用于显示，保留到下一版再删。
- 旧存档：计划只读日志和存档，旧档也按同一规则算，不需要迁移。
- 插件接口：插件读到的剧情轮号不变。

## 第 2 步结论（本机 214 局剧情存档对照）

- 按「每轮一份输入、一份正文」检查：现行隐藏名单有 21 局出问题，行计划只有 2 局（同一局及其备份）。后者是很旧的存档，第 8 轮正文只写成了替换、没有可画的行，两套逻辑结果相同。
- 前端规则与 `planShowsRow` 在全部存档上给出的差异逐行一致。
- 推导规则在对照中补了三条：开场和旧存档没记轮次号的行，按展示投影的推算（开场第 1 轮、每条玩家输入加 1）；修复把多轮挤进同一步时，那一行不代表任何一轮，各轮仍用原来的行；种子消息只按一步的最后一条判断。

## 第 3 步之前必须解决

视图可能只拿到最近一段历史（打开对话时的窗口）。此时行计划带 `from`：更早的轮次不由它判断。白名单切换后，窗口之前的行不能因为「计划里没有」就被藏掉。

调查结果：

- 长存档的浏览器视图**一直**是窗口：`readOpeningWindow` 只取最近 48 行存档，玩家往上滚、遇到没有投影的楼层时再往前扩 120 行（`requestOlderHistory`）。宿主自己的对话页也分页，首屏约 50 条消息（十几轮），通常比 Tavern 的窗口短。
- 行计划只需要每行的 `role / turn / greeting`。存储层已经为每行存了这份摘要（分页条目里的 `message.session`，`sessionSummaries`），会话状态就是用它拼出来的。本机最大一局 479 行，冷读 14 毫秒、热读不到 1 毫秒，计划本身 0.04 毫秒。
- 但这份摘要按快照缓存，每次写入都是新快照，等于每轮全量扫一遍分页索引。这违反「每轮不做全量历史读取」的原则（见长存档性能测量）。
- 窗口之前确实会有该藏的行：本机 22 局长存档里有 4 局，窗口之前有 3～5 个原生轮要藏（修复写入的整段、重新生成的尝试轮）。普通游玩里，早先重新生成过的轮次也会落在窗口之前。

要求：每轮开销不随游戏长度增长（O(1)）；打开对话时也不能扫全部存档行（长存档测量对 `summary-history-read` 有硬性断言）。

考虑过、放弃的做法：

- 每次视图都读全部行摘要：每轮全量扫分页索引。
- 增量轮次表（按 `readChangedIndices` 的 `layoutFrom` 只重读变了的行）：每轮 O(变化)，但进程里第一次打开某局仍要整份读一次，违反上面第二条。
- 窗口之前一律原样显示、且不扩展窗口：往上滚会露出旧正文和触发卡。

**采用：按视图已有的窗口算（`planTranscriptWindow`）。**

- 存档行就用视图本来就读进来的那一段（最近 48 行，往上滚扩展后更多），不额外读存储。
- 会话日志从末尾往回找到窗口第一轮的 `turn/start`，只折叠这一段（加上排在它之前的玩家输入）。原生轮号沿日志单调增长，窗口里各轮的重写（重新生成、修复）都发生在它们自己的回合之后，所以都在这一段里。
- 窗口第一轮之前的原生轮不判断（`transcriptFrom`），页面按宿主原样显示。宿主首屏通常比 Tavern 的窗口短；玩家往上滚到窗口之外时，渲染器已有的机制（没有投影的旧楼层触发 `requestOlderHistory`）会把窗口往前扩，扩完这些轮就进入计划。扩展期间，旧楼层的正文本来就显示「正在读取历史内容…」占位。
- 下发的是例外表（`transcriptTurns`）：只列「不是画自己输入和正文」的原生轮，按轮号分键，走视图同步已有的分键增量通道；前端按键查表。
- 每次视图的开销只和窗口大小有关：单测核对 300 轮和 3000 轮的局访问的日志事件数相同；本机 22 局长存档上，窗口内结论与全量计算逐行一致。

第 3 步要处理：完整视图（短存档、旧存档）按全量算；拿到分页而非窗口的完整视图（`isScopedMessages`）目前不下发计划，前端此时保持现行逻辑。

## 第 3 步结论

- 前端 `createTurnHistoryProjection` 只按计划显示：输入类行看 `input`，正文、尾行、错误行看 `reply`；宿主提示行（context）随整轮，两者都为 0 才藏。窗口第一轮之前的原生轮原样显示。7 个名单函数、localStorage 三份名单（加载时清掉）、assistant-renderer 按名单的提前返回都删掉了；renderer 改为计划不画的正文不渲染。
- 重新生成并进计划（服务端 `setRegeneration`）：正在被替换的旧正文那一轮只留输入；没有玩家输入的尝试轮（插件唤醒，宿主画「收到执行请求」卡）只画正文，运行中和结束后、正文落定前都是。
- 补了一条推导规则：回退替换盖住最后一轮的玩家输入时，这一轮已被回退，不再算「失败待重试」的 `open`。清理失败轮写的是 user 墓碑、不盖输入，仍保留重试。
- 后台 Agent 会话没有计划，仍按它自己的回退轮整轮隐藏。
- #311 的日志脱敏成夹具（`tests/fixtures/transcript/issue-311.json`），计划只画开场与剧情轮 2、3、5、12 各一份。

## 风险

- **白名单藏多了**：计划漏算的行会被藏，症状是「整楼不见」，正是现在要消除的那类。用 `open` 兜住进行中的轮；第 2 步对照期间凡是两套结果不同都记日志。
- **宿主行结构变化**：前端只依赖 `data-chat-turn` 与 `data-chat-flow-kind`，和现在相同，不增加新依赖。
- **工作量**：第 1、2 步各约 1 天，第 3 步约 1～2 天，主要花在真实宿主验收。

## 故事楼层折叠（`story-rounds.js`）

行计划回答「宿主画的哪一行藏起来」；自有故事视图要的是另一个问题：「当前存档有哪些楼层」。`tavern-plugin/lib/domain/story-rounds.js` 只读会话日志就能回答，不需要存档楼层，也不产生行计划：

- 按宿主的方式折叠模型消息面（追加到尾部；replace 取代它遮住的那段），再沿消息面顺序配对：玩家输入（`user/message`，source kind 为 `user`，含编辑后的替换与修复副本）＋该轮已结算（`completed`/`max-tokens`）的模型正文为一层；正文的故事轮取 `source.tavernStoryTurn`，没有时取原生轮号，与行计划同一规则。
- 不成楼层：frame 上下文等插件消息、空正文、运行中的回合（放进 `open`）、失败/中止/中断回合（含从未写 `turn/end` 就被下一轮接上的回合）、重新生成尝试轮自己的正文（投影落定后经 replace 成为原楼层的正文）。
- `abandoned` 列出不再是故事的玩家输入及原因：失败轮的结束原因，或 `rolled-back`（被空墓碑遮住）、`replaced`。被打断（aborted/interrupted）后、下一轮随即认领了玩家输入的回合记为 `superseded`（故事视图排队自动打断，或玩家又发了一条）：玩家已经往下走，不再当作「上一轮已中断」报告；error 结束的回合不算（宿主出错后暂停队列，失败要报告）。
- 每层的 `history` 沿当前正文的替换来源（`sourceEventSeqs`）列出这一轮模型自己的每次生成（追加正文，原始文本）；替换（结算投影、重新生成落定、编辑、结果切换）只是某次生成的呈现，不另列。`current` 标出当前替换代表的那次生成：替换带 `tavernResultSeq` 时取它，否则取它覆盖的最新一次生成。`reply` 仍是当前节点（文本可能是正则处理后的模型上下文文本）。
- 只读事件、不改调用方：服务端与浏览器共用。文件不 import 任何模块、不用 Node/DOM API，可直接 `// @include-domain story-rounds.js` 嵌入客户端；导出 `createStoryRoundsFold()`（按序增量喂入，重复事件跳过）与 `foldStoryRounds(events)`。

稳定性：输出字段（`floors[].story/inputs/reply/history`、`abandoned[].reason`、`open`）只加不改，供 fork 的故事视图插件依赖；现有行计划与其调用方不受影响。窗口不从日志开头起时，跨窗口的 replace 按 `sourceEventSeqs` 尽量还原，窗口内楼层可信、窗口第一轮之前不保证。窗口起点落在回合中间（`turn/start` 在窗口外）时，此前的输入按该轮随后的 `step/*`、追加正文的 `data.turn` 或 `turn/end` 归属；都没有时 `turn` 为 `null`，只进 `open`，不列入 `abandoned`。测试见 `tests/story-rounds.test.mjs`（含 #311 夹具）。
